# AI Tool Usage Disclosure

## Tools

- **Claude Code** (Anthropic), desktop app, from 22 September 2026.
  - **Claude Opus 5.5** for the main coding work (regex patterns, detection rules, tests).
  - **Claude Sonnet 5** for quick, smaller questions. The session has limited time and tokens, and a long conversation is sent again as input with every new request, so I kept small questions in a separate, cheaper conversation.

## How I used it

Claude Code is very helpful in the coding process. With AI I spend more time orchestrating the code than writing it from scratch, and I can focus on the logic: handling edge cases and making sure the rules are not overfitted to the available data.

**Planning.** First, I used the AI to organise my plan for the challenge. I wrote my own to-do list (write the regex for the PII labels that had none, add rules to `detect_pii`, create the GitHub repo, and so on) and discussed it with the AI. It pointed out that my Python version (3.9) was older than the one used in the project's Dockerfile (3.11). I ran all the setup commands myself in the terminal: creating the virtual environment, installing requirements, `git init`, the first commit and pushing to GitHub.

**Code structure.** The AI suggested putting the de-identification code in its own file. I agreed, to make the code more modular, so it is now in `src/deid.py`.

## Task 1: De-identification

**Generated by the AI:** the regex patterns and rules in `src/deid.py`, the tests in `tests/test_deid.py`, the scripts I used to score results per label and per hospital, and the edge-case probes. The AI also turned my draft notes into the de-identification section of `REPORT.md`; I reviewed and edited it.

**Regex patterns.** The AI was most helpful with the name pattern, because a name has many details. I asked it for ideas of what a name pattern should include, and it gave useful ones: inner capitals (McDonald), apostrophes (O'Brien), particles (van der Berg), all-caps names, initials, and titles such as Dr. and Mr. kept outside the name.

**Where I questioned or changed the AI's output:**

- **Overfitting to the dataset.** The AI's first rule for patient names without a "Patient:" word looked for a date of birth or a patient ID right after the name, exactly as in the public templates. I pointed out that a patient ID after the name only happens in this dataset by coincidence. The data card confirmed that the hidden set has new formats, so we made the cues more general (any short code plus digits instead of only the known ID formats, and an age cue such as "49 y") and added general versions of every rule (IDs after any ID keyword, written-out dates, `+` phone numbers, street shapes for addresses).
- **Names derived from clinician emails.** I first rejected this rule because adding or removing it didn't change the results on the public data, and I asked to remove it. The AI then showed that the data dictionary defines emails as clinician contacts (all 120 training emails match the clinician's name), and that in a note with no trigger word, such as `Follow-up arranged — Deepa Naidu (deepa.naidu@...)`, the name leaks without it. I agreed to restore it, with one change: it no longer overrides a name already found as a patient, in case the hidden data has patient emails.
- **A patient who is a doctor.** I asked what happens if the patient has "Dr." before their name. Testing `Patient: Dr. Anna Keller` (a test example, not a case from the dataset) showed a real bug: she was labelled as a clinician because the title rule ran first. The fix was to reorder the rules so explicit roles come first, and to let the title and email rules keep the label of a name already found. A story-like mention with no role word (`Dr. Anna Keller was admitted...`) is still a limitation.
- **My own draft code.** Early on, I pasted a draft name pattern into `src/baseline.py`. It used the same name (`NAME`) as the AI's pattern and would have overridden it, which I found out when the AI checked the file. I removed my draft lines.

**Mistakes by the AI that were caught:**

- The AI first said training note `TRN-BER-0040` was mislabelled in the dataset, because all its offsets were shifted by one character. Checking the files against `MANIFEST.sha256` showed it wasn't: I had typed an extra "f" into "Clara" by accident while using Ctrl+F. With the "f" removed, the file matched the original checksum, so I restored it and did not report it as a data error.
- The AI widened the date-of-birth look-back window, which labelled 49 Hyderabad visit dates as birth dates. It was caught by re-running the per-label scores and replaced with a "closest cue wins" rule.
- In the first version of the tests, one "expected to fail" test used a chained comparison that is always false in Python, so it would have passed for the wrong reason. It was fixed before running.

**How I verified the output:** the official evaluator (`make evaluate`), scores per label and per hospital on both train and validation, about 30 edge cases that are not in the data, the full test suite (`make test`), and reading through the tests and the commented code myself.

**Tests.** The AI generated the test cases and I reviewed them. It suggested marking the known limitations as tests that are expected to fail (`xfail`), so they stay visible for future work, and so we notice if one unexpectedly starts passing.
