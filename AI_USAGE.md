  - **Claude Opus 5.5** for the main coding work (regex patterns, detection rules, tests).

## How I used it

Claude Code is very helpful in the coding process. The nice thing about AI is that I spend more time orchestrating the code rather than writing it from scratch, and I can focus on the logic: handling edge cases and making sure the rules are not overfitted (exactly fitted) to the available data.

First, I used the AI to organise my plan for the challenge. I wrote my own to-do list (write the regex for the PII labels that had none, add rules to `detect_pii`, create the GitHub repo, and so on) and discussed it with the AI. It pointed out that my Python version (3.9) was older than the one used in the project's Dockerfile (3.11). I ran all the setup commands myself in the terminal: creating the virtual environment, installing requirements, `git init`, the first commit and pushing to GitHub.


## Task 1: De-identification

Generated by the AI: the regex patterns and rules in `src/deid.py`, the tests in `tests/test_deid.py`, the scripts I used to score results per label and per hospital, and the edge-case probes. I asked the AI to review my notes about this phase before I place them in REPORT.md document so I can verify if something was misunderstood.

Regex patterns: The AI was most helpful with the name pattern, because a name has many details. I asked it for ideas of what a name pattern should include, and it gave useful ones: inner capitals (McDonald), apostrophes (O'Brien), particles (van der Berg), all-caps names, initials, and titles such as Dr. and Mr. kept outside the name.

**Where I questioned or changed the AI's output:**

- Overfitting to the dataset: The AI's first rule for patient names without a "Patient:" word looked for a date of birth or a patient ID right after the name, exactly as in the public templates. I pointed out that a patient ID after the name only happens in this dataset by coincidence. The data card confirmed that the hidden set has new formats, so we made the cues more general (any short code plus digits instead of only the known ID formats, and an age cue such as "49 y") and added general versions of every rule (IDs after any ID keyword, written-out dates, `+` phone numbers, street shapes for addresses).
- Names derived from clinician emails: I first rejected this rule because adding or removing it didn't change the results on the public data, and I asked to remove it. The AI then showed that the data dictionary defines emails as clinician contacts (all 120 training emails match the clinician's name), and that in a note with no trigger word, such as `Follow-up arranged — Deepa Naidu (deepa.naidu@...)`, the name leaks without it. I agreed to restore it, with one change: it no longer overrides a name already found as a patient, in case the hidden data has patient emails.
- A patient who is a doctor: I asked what happens if the patient has "Dr." before their name. Testing `Patient: Dr. Anna Keller` (a test example, not a case from the dataset) showed a real bug: she was labelled as a clinician because the title rule ran first. The fix was to reorder the rules so explicit roles come first, and to let the title and email rules keep the label of a name already found. A story-like mention with no role word (`Dr. Anna Keller was admitted...`) is still a limitation.
- My own draft code:Early on, I pasted a draft name pattern into `src/baseline.py`. It used the same name (`NAME`) as the AI's pattern and would have overridden it, which I found out when the AI checked the file. I removed my draft lines.

Mistakes by the AI that were caught:

- The AI first said training note `TRN-BER-0040` was mislabelled in the dataset, because all its offsets were shifted by one character. Checking the files against `MANIFEST.sha256` showed it wasn't: I had typed an extra "f" into "Clara" by accident while using Ctrl+F. With the "f" removed, the file matched the original checksum, so I restored it and did not report it as a data error.
- The AI widened the date-of-birth look-back window, which labelled 49 Hyderabad visit dates as birthdates. It was caught by re-running the per-label scores and replaced with a "closest cue wins" rule.
- In the first version of the tests, one "expected to fail" test used a chained comparison that is always false in Python, so it would have passed for the wrong reason. It was fixed before running.

How I verified the output: the official evaluator (`make evaluate`), scores per label and per hospital on both train and validation, about 30 edge cases that are not in the data, the full test suite (`make test`), and reading through the tests.

Tests: The AI generated the test cases and I reviewed them. It suggested marking the known limitations as tests that are expected to fail (`xfail`), so they stay visible for future work, and so we notice if one unexpectedly starts passing.

## Task 2: Structured extraction

Generated by the AI: the move of the extraction code to `src/extraction.py` (as a git rename, so the history is kept), the first version of the synonym dictionaries, the negation rules, the unit conversion, the new smoking and allergy rules, the tests in `tests/test_extraction.py`, and the scripts that score each field and list every error.

My own input:

- Medical terms: I discussed common medical wordings with my brother, who is a medical doctor, and used the AI to generate more synonyms. I added heart failure terms to the dictionary myself (`HF`, `a fib`, `congestive heart failure`, and the longer "heart failure with ... ejection fraction" terms). The AI pointed out that the long terms are already covered by "heart failure", so they are harmless but not needed.
- A mistake of my own: I also added "ischemic heart disease" to the acute coronary syndrome list. The AI flagged it before building the next step: in the ground truth, all 8 notes with that wording are labelled coronary artery disease, and my line added ACS wrongly to all of them. I asked why the two are separate categories at all; the answer (they are separate labels in the data dictionary, and one is a long-term condition while the other is a sudden event) convinced me, and I removed the line.
- Understanding what does the smoke testing do: After the code move, I noticed that all tests passed although I had not written any task 2 code yet, it was all about creating synonyms so far. It was that the only extraction test checked that the output has the 9 fields, not their values, and that is the idea of smoke testing basically, I verified this thought with the AI.
- The AI proposed treating "possible", "suspected" and "query" as not active, and flagged it as a decision for me; I kept it. I also kept its choices not to map an aspirin allergy to NSAID and to read "denies smoking" as never, and now they are listed as limitations in the report.

How ambiguous wordings were decided: by checking the correct answers that come with the data (the labels in data/train.jsonl and data/validation_ground_truth.jsonl). The AI ran a script that found every note containing an unclear wording and counted which diagnosis those notes are labelled with. For example, plain "diabetes mellitus" appears in 15 notes and all 15 are labelled type 2 diabetes, and the 3 notes with "IHD" are all labelled coronary artery disease.
Mistakes by the AI that were caught:

- Its first whole-word rule treated a hyphen as part of the word, so `CKD-3` was not recognised. Caught by the per-field scores.
- It had not included `APX`, the short form of apixaban used in one Hyderabad note. Caught by the per-field scores.
- "Warfarin stopped due to bleeding" still counted warfarin as a current drug. Caught by an edge case.
- German compound words like "Kontrastmittelallergie" were missed. Caught by an edge case.
- The first test file did not really test whole-word matching: when the AI broke that rule on purpose, all tests passed because all the abbreviation examples were lowercase. An all-caps example was added, and now the break is caught.

How I verified the output: the official evaluator, scores for every field on train and validation with a list of every error, edge cases that are not in the data, and "breaking the code on purpose" to check that the tests fail when they should.
